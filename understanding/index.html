Understanding STEEX

Explainers for how the STEEX multi-agent trading system works, plus proposals for improving it. Written against branch fix/langgraph-parallel-traces.

The one-paragraph mental model

A cron job fires scheduler/run.sh, which (after market/lock gates) calls run_manager.py, which builds a LangGraph graph from config/agents.yaml for the requested mode. LangGraph orchestrates the flow between agents — running prep agents sequentially, fanning out three analysis variants in parallel, merging them via a meta-agent, and handing everything to a supervisor manager that makes the final trade decision. Each agent is itself a Claude CLI subprocess running its own tool-use loop, where every tool is delivered over MCP by our steex server (wrapping the real trading code). If a critical agent fails, the graph falls back to deterministic rules-based logic. Results are traced to data/agents/sessions/, surfaced on a dashboard, and a weekly learning loop post-mortems the trades and re-tunes the scoring weights.

1 · How We Use LangGraph

How LangGraph is wired into STEEX, the core syntax, and how to add a new agent.

1.1 What LangGraph does for us

LangGraph builds stateful, graph-structured agent workflows. Instead of a hard-coded for loop calling agents in sequence (what STEEX used before commit 105e5df), we describe the pipeline as a directed graph of nodes and edges and let LangGraph drive execution — including parallel nodes and result merging.

ConceptIn STEEXWhere
StatePipelineState TypedDict that flows through the run; each node returns a partial update.src/agents/state.py
GraphStateGraph built dynamically from the mode config.src/agents/graph.py
NodesFunctions that call a sub-agent and return its conclusion + trace.src/agents/nodes.py

Important nuance: the individual agents are not LangChain/LangGraph LLM objects. Each agent node shells out to the claude CLI as a subprocess. LangGraph orchestrates the flow between agents; the Claude CLI runs the agentic loop inside each agent. Deliberate — each agent gets the full Claude Code tool-use loop with MCP, while LangGraph handles fan-out/fan-in and conditional routing.

1.2 The state object

class PipelineState(TypedDict):
    mode: str
    task_context: str
    today: str
    run_id: str
    conclusions: dict[str, dict]                       # name -> agent conclusion
    variant_conclusions: Annotated[list[dict], add]    # parallel writes
    traces: Annotated[list[dict], add]                 # parallel writes
    manager_decision: Optional[dict]
    screen_data: Optional[dict]
    abort: bool
    abort_reason: Optional[str]

Each node returns a partial dict; LangGraph merges it into state. Most keys overwrite — but variant_conclusions and traces use the add reducer.

The Annotated[list, add] reducer (the thing that broke and got fixed)

When three variants run in parallel in the same superstep, they all write traces at once. A normal channel raises InvalidUpdateError on the second concurrent write. The add reducer concatenates instead of overwriting.

Rule for node authors: a parallel node returns only its own new entry — return {"traces": [my_trace]} — never the accumulated list, or entries duplicate. This was the root cause fixed in commit cffe950.

1.3 How the graph is built

build_graph() constructs the graph at runtime from the ModeConfig for the running mode.

Core syntax we use

from langgraph.graph import StateGraph, END
from langgraph.types import Send

graph = StateGraph(PipelineState)            # graph typed over our state
graph.add_node("risk", risk_node_fn)         # register a node
graph.add_edge("data", "risk")               # unconditional edge
graph.set_entry_point("data")                # where execution starts

graph.add_conditional_edges(                 # router fn -> destination
    "risk", route_after_agent,
    {"continue": "fan_out", "fallback": "fallback"},
)
graph.add_edge("report", END)                # terminal edge

Fan-out / fan-in (the parallel variants)

# fan-out node returns a list of Send objects -> run concurrently
def node(state):
    return [Send(agent_name, state) for agent_name in parallel_agents]

All variants write into variant_conclusions (via the reducer). merge_variants runs after all complete (fan-in) and asks the meta_analysis agent to synthesize consensus.

1.4 The graph for screen mode

flowchart LR data --> risk risk -->|ok| fan_out risk -->|critical fail| fallback fan_out --> c[analysis_conservative] fan_out --> a[analysis_aggressive] fan_out --> m[analysis_momentum] c --> merge[merge_variants
meta_analysis] a --> merge m --> merge merge --> manager manager --> save[save_screen] save --> report --> EN([END]) fallback --> EN
  • data → risk: sequential sub-agents.
  • risk is critical: on failure, routes to deterministic fallback.
  • fan_out: emits three Sends → variants run in parallel.
  • merge_variants: fan-in; runs the meta-agent over all variant conclusions.
  • manager: synthesizes the final decision; post-actions run at the end.

1.5 How a node runs an agent

cmd = [
    claude_bin,
    "-p", f"{system_prompt}\n\n---\n\n{task_message}",
    "--output-format", "json",
    "--max-turns", str(max_turns),
]
if needs_tools:
    cmd.extend(["--mcp-config", get_mcp_config(ctx)])
    tool_perms = [f"mcp__steex__{t}" for t in allowed_tools] or ["mcp__steex__*"]
    cmd.extend(["--allowedTools", ",".join(tool_perms)])

So the full chain is LangGraph node → Claude CLI subprocess → MCP tools.

1.6 Adding a new agent — step by step

The system is declarative: agents are defined in YAML, not code. Four places.

Step 1 — define it in config/agents.yaml

agents:
  sentiment_scout:
    prompt: "sentiment_scout"
    conclusion: "SentimentConclusion"
    max_turns: 12
    needs_tools: true
    allowed_tools:
      - get_signal_confidence
      - run_screening_variant
    external_servers: [alphavantage]

Step 2 — add its conclusion model in src/agents/conclusions.py

class SentimentConclusion(BaseModel):
    bullish_tickers: List[str]
    bearish_tickers: List[str]
    market_mood: str
    reasoning: str

Step 3 — write the prompt

Disk override data/agents/prompts/sentiment_scout.md (preferred for iteration), or code default src/agents/prompts/sentiment_scout.py exporting SENTIMENT_SCOUT_AGENT_PROMPT. Instruct it to output JSON matching the model.

Step 4 — wire it into a mode

modes:
  screen:
    sub_agents: [data, risk, sentiment_scout]   # runs after risk, before fan_out
    parallel_agents: [analysis_conservative, analysis_aggressive, analysis_momentum]

No graph code changes needed — build_graph() wires it from config. Add it to critical_agents if its failure should abort the run.

1.7 Gotchas

  • State must be JSON-serializable (also what LangSmith would trace). Conclusions stored as .model_dump() dicts.
  • Parallel nodes return only their own slice of variant_conclusions/traces.
  • max_turns is per-agent (caps the Claude tool-use loop, not the graph).
  • A failed critical agent routes the whole run to the deterministic fallback.
  • The graph is rebuilt every run from config — change agents.yaml, no redeploy.

2 · Evaluation — Current State & Upgrades

Two notions of "evaluation" are easy to conflate here.

  1. Strategy evaluation — is the strategy making money? Backtests, post-mortems, the learning loop. Mature.
  2. Agent evaluation — are the agents behaving well? Largely absent today — the biggest opportunity.

2.2 The gap: we don't evaluate the agents

An agent run is "successful" if the subprocess exits 0 and output parses. That's a liveness check, not a quality check. No systematic answer to: did it call the right tools in order? Are variants actually diverse? Did the manager hallucinate a ticker no agent proposed? How often does each agent fall back? Are prompts improving after evolution?

2.3 Proposed evaluation process

Layer 1 — per-run automatic assertions (cheap, every run, no LLM)

CheckSignal
Conclusion schema valid (record as metric)—
Required tool called first (e.g. sync_broker)Prompt adherence
Manager buys ⊆ union of variant candidatesGrounding (no hallucinated tickers)
Variant diversity (Jaccard overlap)Are variants different?
Turn count vs capAgent struggled?
Latency vs baseline / tool error rateRegression / health

Layer 2 — LLM-as-judge (periodic)

Separate Claude call with a rubric: groundedness, decision quality, instruction adherence (1–5). Store alongside the trace.

Layer 3 — golden-set regression suite (on every prompt change)

~20–30 frozen scenarios with expected behaviors. Replay whenever a prompt is edited or evolved — catches regressions before production. Critical since evolve_prompts can auto-rewrite prompts.

Layer 4 — outcome attribution

Tag each executed trade with the agent/variant that produced it, so the post-mortem can say which variant performed best. No such link exists today.

2.4 Relation to observability

Evaluation and observability are two views of the same trace data. Observability = "what happened" (the dashboard). Evaluation = "was it good" (scores derived from the same traces). Practical upgrade: compute Layer-1 metrics in trace post-processing and store them in dashboard.db, so the dashboard shows trend lines (fallback rate, judge score, diversity) rather than just the latest snapshot. Longer term, LangSmith gives proper trace trees + dataset evals; state is already JSON-serializable for it.

3 · Memory Strategies

What persists today, and how to build persistent context that survives across sessions and is shared across agents.

3.1 What we have today

Memory exists but is a patchwork of files with different lifetimes and no shared "what do we know" layer agents read at run start.

TierWhatLifetime
1 · In-run statePipelineState + MCP module globalsEphemeral (discarded at run end)
2 · Per-run tracesdata/agents/sessions/*.json30 days; write-only — agents don't read past runs
3 · Domain statepositions/trades/screen_results, cache.dbIndefinite
4 · Learning knowledgelearning_journal / config_history / gapsIndefinite
5 · Prompt memoryevolved prompts (evolution_enabled: false)Disabled

There is no LangGraph checkpointer. graph.compile() is called with no checkpointer=, so LangGraph persists nothing between runs.

BoundaryCarries overMechanism
tool → tool (same agent)intermediate resultsMCP module globals
agent → agent (same run)conclusionsPipelineState.conclusions

run → run (general)nothing—

The big hole: agents start every run with a blank slate.

3.2 Goal: persistent, shared context

Option A — turn on LangGraph checkpointing (lowest effort, biggest immediate win)

from langgraph.checkpoint.sqlite import SqliteSaver
checkpointer = SqliteSaver.from_conn_string("data/checkpoints.db")
graph = build_graph(...).compile(checkpointer=checkpointer)
final_state = graph.invoke(initial_state,
    config={"configurable": {"thread_id": f"{mode}-{today}"}})

Gives resumable runs, cross-run threads, and time-travel debugging.

Option B — shared memory store as MCP tools (best for cross-agent semantic memory)

@mcp.tool()
def recall_memory(topic: str, limit: int = 5) -> str:
    """Retrieve relevant learned facts. Call at the start of reasoning."""
    return _safe_json(memory_store.search(topic, limit))

@mcp.tool()
def remember(fact: str, kind: str, tickers: list[str] | None = None) -> str:
    """Persist a durable observation for future runs and other agents."""
    memory_store.add(fact=fact, kind=kind, tickers=tickers, ts=now())
    return _safe_json({"stored": True})

Back with SQLite (structured/auditable) + optional vector index for semantic recall. LangGraph's Store abstraction also fits.

Option C — pre-run "context brief" node (cheap glue, high leverage)

A front node assembling a compact brief from existing artifacts (recent sessions, open gaps, recent config changes, current regime) into task_context. No new storage; just stop discarding what we already write.

3.3 Recommended path

  1. Now: Option C (context brief) — immediate, no new infra.
  2. Next: Option A (SQLite checkpointer) — resumability + run-to-run threads.
  3. Then: Option B (MCP memory tools, vector-backed) — true shared semantic memory, with writes visible in traces.

Design notes: make memory writes appear in traces (auditable/evaluable); scope by kind; set TTL/decay (markets change); let the weekly learning loop curate — promote transient observations, expire stale ones.

4 · Multi-Agent Orchestration Pattern

The pattern, why it was chosen, and alternatives worth considering.

4.1 Current pattern: Supervisor + Parallel Fan-out/Fan-in + deterministic fallback

A deliberate hybrid, expressed declaratively in agents.yaml and assembled by build_graph().

  1. Sequential sub-agents — prep runs in order (data → risk).
  2. Parallel fan-out/fan-in — three analysis variants (conservative, aggressive, momentum) run concurrently; a meta-agent synthesizes.
  3. Supervisor / manager — one accountable agent makes the final decision.
  4. Conditional execution gate — execution runs only if the manager approved trades.
  5. Critical-agent abort → deterministic fallback — the safety net that makes an LLM trading system tolerable.

The consensus mechanism (why three variants)

The meta-agent looks for agreement, not averages: all 3 = high-conviction; 2 of 3 = consensus (included); 1 = speculative (excluded). It's an ensemble for robustness — three investing personalities voting.

flowchart LR data --> risk risk --> fan[fan_out] risk -->|critical fail| fb[deterministic fallback] fan --> v1[conservative] fan --> v2[aggressive] fan --> v3[momentum] v1 --> mg[merge / meta] v2 --> mg v3 --> mg mg --> man[manager · supervisor] man -->|approved| ex[execution] man -->|no| rep[report] ex --> rep fb --> EN([END]) rep --> EN

4.2 Why this pattern

It's a money-handling, autonomous, scheduled system:

  • Supervisor → one accountable decision-maker; only the manager can approve orders.
  • Ensemble → counters LLM variance and single-strategy bias; a pick must survive disagreement.
  • Parallel, not sequential variants → independent inputs, no priming.
  • Deterministic fallback → non-negotiable for unattended autonomy; arguably the most important decision.
  • Declarative topology → other modes reuse the machinery; a new mode is a YAML edit.

Supervisor for accountability, ensemble for robustness, fallback for safety.

4.3 Alternatives

PatternProCon / verdict
A · Hierarchical (team-of-teams)Scales as agents multiplyMore layers/latency; only if agent count grows a lot
B · Swarm / handoffFlexible emergent routingHard to audit/bound; not for the trade path
C · Plan-and-executeAdapts to noveltyNon-deterministic; pilot inside learning only
D · Debate / reflectionBetter decisions, surfaces disagreementMore cost; needs the eval harness to prove it helps
E · Deterministic-by-default, LLM-on-exceptionBig cost savings; agents focus where they matterNeeds an "is this ambiguous?" trigger; strong candidate

4.4 Recommendation

Keep the supervisor + ensemble + fallback core. Highest-value evolutions: (E) deterministic-by-default, then (D) a manager reflection pass (gated by the eval harness), then (C) plan-and-execute inside learning only. Hold off on (A) and (B) until task diversity demands them.

5 · Cron Jobs, Tools & MCP

The scheduled-run flow, the agent reasoning loop, how tools are implemented, MCP, and tool vs skill vs MCP.

5.1 End-to-end cron flow

Nothing about the orchestration is special to cron — cron just invokes the same entry points a human would.

5.2 What an agent's reasoning loop looks like

Each node calls run_agent(), launching the claude CLI as a subprocess. Inside, Claude runs its standard tool-use loop: read → call tool → receive result → reason → … → final answer, bounded by --max-turns. On finish, STEEX parses the JSON envelope, extracts tool calls into the trace, and validates the output against the agent's Pydantic conclusion model; failures write a failures/*.log and (for a critical agent) trigger the fallback.

flowchart LR subgraph outer [LangGraph · agent → agent] n1[node A] --> n2[node B] end subgraph inner [Claude CLI · tool → tool] t1[reason] --> t2[call tool] --> t3[result] --> t1 end n1 -.spawns.-> inner

Two nested loops: LangGraph's outer graph and Claude's inner tool-use loop.

5.3 Tools and how they're implemented

All STEEX tools live in one FastMCP server, src/agents/mcp_server.py. Each is a function decorated with @mcp.tool() wrapping a QuantManager method, returning JSON.

from mcp.server.fastmcp import FastMCP
mcp = FastMCP("steex")

@mcp.tool()
def get_regime() -> str:
    """Detect current market regime (risk_on / cautious / risk_off / crisis)."""
    mgr = _init_manager()          # lazy-init on first call
    _regime = mgr.get_regime()
    return _safe_json(_regime)
  • Runs as a stdio subprocess started by the CLI (JSON-RPC over stdin/stdout → rich output goes to stderr).
  • Lazy init — builds QuantManager only on the first tool call.
  • Per-call config — --paper/--dry-run decide paper/live and simulated orders.
  • ~40 tools: data, risk, analysis, execution, research/learning, reporting.
  • Per-agent allowlist restricts what each agent can touch (only execution places orders).

External MCP servers add market data: alpaca, alphavantage, polygon — granted via external_servers.

5.4 What MCP is

MCP (Model Context Protocol) is an open standard connecting an LLM to external capabilities. A server advertises tools, resources, and prompts; a client (the Claude CLI) discovers them and routes tool calls. "USB-C for AI tools."

flowchart LR cli[Claude CLI · MCP client] --> s1[(steex · 40 tools)] cli --> s2[(alpaca · quotes/orders)] cli --> s3[(alphavantage · indicators)] cli --> s4[(polygon · aggregates/news)]

The agent never imports our Python directly — it asks (via MCP) for run_screening, the CLI forwards it, our server runs the real pipeline and returns JSON. Keeps the LLM sandboxed behind an explicit, allowlisted interface — what you want when a "function" can place a real trade.

5.5 Worked example: adding a tool

@mcp.tool()
def get_sector_exposure() -> str:
    """Return portfolio exposure by sector as a fraction of equity.
    Use this to check concentration before approving new buys."""
    mgr = _init_manager()
    positions = mgr.position_manager.get_all_positions()
    equity = mgr._get_portfolio_value()
    by_sector = {}
    for pos in positions:
        sector = mgr.get_sector(pos.ticker)
        by_sector[sector] = by_sector.get(sector, 0.0) + pos.market_value
    weights = {s: round(v / equity, 4) for s, v in by_sector.items()}
    top = max(weights, key=weights.get) if weights else None
    return _safe_json({"by_sector": weights, "most_concentrated": top})
risk:
  allowed_tools:
    - sync_broker
    - get_regime
    - assess_portfolio_risk
    - get_sector_exposure      # <-- new

The docstring is what the model sees (write it for the model); the return must be JSON-serializable; the allowlist entry is what actually exposes it. Mention it in the agent's prompt so it knows when to use it.

5.6 Tool vs Skill vs MCP

ToolSkillMCP
WhatA single callable function (name + description + schema)A bundle of instructions/knowledge teaching how to do a taskA protocol/transport delivering tools (and resources/prompts)
GranularityOne actionA whole workflowA connection exposing many tools
In STEEXrun_screening, execute_entriesThe agent prompts (procedural know-how)The steex server + alpaca/polygon/alphavantage
AnalogyA verbA playbookThe plumbing delivering the verbs

A tool is capability ("you can do X"). A skill is procedure ("how/when to do X well") — it may use tools but adds none. MCP is delivery (the portable way a tool reaches the model).

Better ways to give agents abilities?

  • Actions: tools, delivered via MCP — gives reuse, sandboxing, allowlisting (the boundary that stops an unintended trade). Our case.
  • Know-how: a skill/prompt beats more tools. If the manager mis-weights consensus, fix the guidance, not the tools.
  • Read-only context: MCP resources (unused today) are lighter than wrapping every read in a tool.

For STEEX: keep MCP-delivered tools for anything touching the broker/pipeline, lean on prompts/skills for reasoning quality, consider MCP resources for pure-read context. This connects to the memory plan, where recall/remember are MCP tools precisely so memory access shows up in traces.
